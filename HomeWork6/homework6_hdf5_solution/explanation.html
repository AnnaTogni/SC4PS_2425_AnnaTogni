HomeWork 6: Chunked DAXPY with HDF5

This page explains what the C program in main.c is doing, step by step, with the goal of making the logic natural for a physics PhD student who is comfortable with numerical methods but may be less familiar with C software structure.

Big Picture

What problem is the code solving?

The mathematical operation is d[i] = a * x[i] + y[i]. In numerical linear algebra this is the classical DAXPY pattern: take one vector, multiply it by a scalar, and add another vector.

The homework asks for two implementations of the same physics-style array operation: one straightforward loop over all indices, and one chunked version where the vector is processed block by block. After that, the program must check that both approaches give the same answer, compute a sum over each chunk, and store the results in an HDF5 file.

You can think of the chunked version as dividing a long detector signal, grid field, or Monte Carlo data stream into smaller blocks that are easier to inspect, parallelize, or save.
Step 1

Headers and feature detection

At the beginning of the program, the code includes standard C libraries such as stdio.h, stdlib.h, and math.h. These are used for printing, memory allocation, and numerical checks.

It also includes glib.h to parse the configuration file, and then checks whether HDF5 headers are available: 

#if __has_include(<hdf5/serial/hdf5.h>)
#include <hdf5/serial/hdf5.h>
#define HAVE_HDF5 1
#endif

This is a practical software-engineering detail. It lets the same source code compile cleanly whether HDF5 is installed or not.

Step 2

The two main data structures

Config

This structure stores the input parameters: vector length, chunk size, the scalar a, and the HDF5 file name.

DataSet

This stores the arrays themselves: x, y, the reference result, the chunked result, the partial chunk sums, and the number of chunks.

A useful way to interpret this is: Config contains the experimental settings, while DataSet contains the measured or computed data.

Step 3

How input is handled

The program supports two modes.

  • NumericalSum-style interactive mode: it asks for N, a, whether all entries of x are equal, whether all entries of y are equal, the chunk size, and the HDF5 output file.
  • Config-file mode: you run ./homework6 --config homework6.cfg and values are read from the text file.

The interactive mode mirrors the earlier course exercise so that the user experience stays familiar. The config mode is useful for reproducibility, since you can save an exact input state and run it again later.

Step 4

Memory allocation

Once the vector length is known, the function allocate_dataset allocates memory for all arrays. This is necessary because the program does not know in advance how large the vectors will be. 

data->x = g_new0(double, config->vector_length);
data->y = g_new0(double, config->vector_length);
data->d_reference = g_new0(double, config->vector_length);
data->d_chunked = g_new0(double, config->vector_length);

In physics language, this is like reserving enough storage for all the degrees of freedom before starting the numerical experiment.

Step 5

The reference calculation

The function compute_reference performs the direct textbook implementation: 

for (gsize i = 0; i < config->vector_length; ++i) {
    data->d_reference[i] = config->alpha * data->x[i] + data->y[i];
    sum += data->d_reference[i];
}

This is the control calculation. It is the simplest and most transparent version, so it is the one used as a benchmark to validate the chunked approach.

Step 6

The chunked calculation

The key homework idea appears in compute_chunked. Instead of looping once over the full vector, the code first identifies which chunk it is in, then loops only over the elements of that chunk. 

for (gsize chunk_index = 0; chunk_index < data->number_of_chunks; ++chunk_index) {
    gsize start = chunk_index * config->chunk_size;
    gsize end = start + config->chunk_size;
    if (end > config->vector_length) {
        end = config->vector_length;
    }
    ...
}

The last chunk may be smaller than the others, so the code explicitly truncates end to the actual vector length. This is exactly the numerical edge case discussed in the assignment.

If your total vector has 25 elements and the chunk size is 8, then the chunks are 8, 8, 8, and 1 element. That final one-element block must still be handled correctly.
Step 7

Partial chunk sums

Inside each chunk, the code computes not only the vector values but also a local sum: 

double partial = 0.0;
for (gsize i = start; i < end; ++i) {
    data->d_chunked[i] = config->alpha * data->x[i] + data->y[i];
    partial += data->d_chunked[i];
}
data->partial_chunk_sum[chunk_index] = partial;

This is numerically meaningful because it introduces a simple reduction over blocks. In larger scientific codes, this is the same kind of pattern used in domain decomposition, MPI reductions, tiled linear algebra, and cache-aware processing.

Step 8

Verification and numerical sanity checks

After computing both versions, the program checks:

  • whether every element of the chunked vector matches the reference vector
  • whether the total sum of all chunk sums matches the reference total
  • what the maximum absolute difference is between the two vectors

This is good scientific computing practice. A faster or more structured algorithm is only useful if it reproduces the correct result within an acceptable tolerance. 

vectors_match = compare_vectors(..., 1e-12, &max_abs_diff);
printf("Sums match: %s\n", fabs(reference_sum - chunked_sum) <= 1e-12 ? "YES" : "NO");
Step 9

Writing the HDF5 output

HDF5 is used because it is a standard scientific format for structured numerical data. The program writes:

  • the input vectors x and y
  • the two output vectors d_reference and d_chunked
  • the array partial_chunk_sum
  • each chunk of d_chunked separately under the group /chunks

This gives you both the global result and the block-by-block structure, which is exactly what the homework requested. 

chunks_group = H5Gcreate2(file, "/chunks", ...);
write_double_dataset(file, "partial_chunk_sum", ...);
write_double_dataset(chunks_group, dataset_name, &data->d_chunked[start], ...);
Step 10

Why the program is written in functions

The code is split into small functions rather than written as one very long main. This is not just a software style preference.

  • load_config handles the input file logic
  • allocate_dataset handles memory
  • compute_reference handles the direct algorithm
  • compute_chunked handles the block algorithm
  • write_hdf5_output handles storage

This separation makes the program easier to debug, easier to extend, and easier to compare with the mathematical structure of the problem.

Step 11

How to read the code as a scientist

A helpful reading strategy is:

  • First read main to understand the overall workflow.
  • Then read compute_reference and compute_chunked to see the numerical core.
  • Then read write_hdf5_output to understand how results are stored.
  • Only after that, look at helper functions such as input parsing and memory cleanup.

This mirrors how one usually approaches a simulation paper: first the physical idea, then the algorithm, then the implementation details.
